# First owner without passwords or bootstrap secrets in chat

This flow uses the authenticated Azure account to prepare the backend, then lets the user choose their own Voqro password in the website. No user password is generated by the agent or passed through Azure.

## 1. Confirm the intended owner

Use the contact email from the authenticated Microsoft identity. Confirm it belongs to the intended owner; a guest `#EXT#` directory principal is not automatically their contact address. If no trustworthy contact email is present, ask for the email address only. Do not ask for a Microsoft password, token or Voqro password.

Prepare the backend environment in a current-user-owned **0600 file outside the Git checkout**, in a private directory. Generate `IDENTITY_BOOTSTRAP_SECRET` with a cryptographically secure random source (at least 32 URL-safe characters). Keep it out of command arguments, source files, terminal output, app URLs and shell tracing. The environment must use `NODE_ENV=production`, `DEMO_MODE=0`, `AUTH_PROVIDER=password`, secure cookies, the exact public frontend origin, and the persistent database/media paths from the deployment guide.

The secret protects only the one-time initial-owner bootstrap. It is not the user's password. The application must consume bootstrap durably so restarting the VM cannot recreate an owner.

## 2. Prepare a protected Managed Run Command

`az vm run-command invoke` does **not** expose protected parameters. Use **Managed Run Command** (`az vm run-command create`) or its ARM REST equivalent.

The [official Linux Managed Run Command documentation](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/run-command-managed) states that named parameters, including protected parameters, are exposed as environment variables to the Linux script. Therefore the constant script can read `VOQRO_ENV_B64`; the secret must not be interpolated into the script source.

The helper prepares a private request body and optional bootstrap-only file without sending any request:

```bash
python3 infra/azure/provision-env-body.py \
  --env-file /private/path/backend.env \
  --output /private/path/provision-env-body.json \
  --bootstrap-file /private/path/owner-bootstrap.txt \
  --location centralindia
```

All paths must be outside this checkout. The input must be a current-user-owned regular **0600** file. Output files are created **0600** without overwriting an existing path. The helper validates the production settings and provider opt-outs. It does not print values, invoke Azure or generate credentials.

The resulting JSON contains a constant `source.script` and `protectedParameters: [{name: "VOQRO_ENV_B64", value: "…"}]`. Base64 itself is not encryption; protection comes from the Azure protected-parameter channel. Keep the local JSON private and short-lived.

After the VM exists and the operator has VM Run Command permissions, send the body with **`@file`**, not an inline secret argument:

```bash
az rest --method put \
  --url 'https://management.azure.com/subscriptions/SUBSCRIPTION_ID/resourceGroups/RESOURCE_GROUP/providers/Microsoft.Compute/virtualMachines/VM_NAME/runCommands/voqro-private-env?api-version=2024-07-01' \
  --body @/private/path/provision-env-body.json \
  --only-show-errors --output none
```

Use the installed Azure CLI's exact path if `az` is not on PATH. Replace only resource identifiers in the URL. Do not use `--debug`, `--verbose`, `set -x`, environment dumps or output-blob logging. Inspect only command provisioning/execution state and sanitized messages afterward.

The script creates `/etc/voqro/backend.env` as root with mode **0600**, and prints only success/failure descriptions. It refuses to replace a different existing file, follow a symlink, or silently broaden permissions. Linux protected parameters are transient process environment values; do not run tracing or unrelated diagnostic commands in that process.

## 3. Let the owner retrieve only the bootstrap secret privately

Create a small **Standard Azure Key Vault** in the approved region solely for this one-time handoff. Confirm it remains covered by the Students subscription and spending limit. Key Vault secret operations add a small variable first-party meter; this is separate from the VM baseline and does not require a paid-plan upgrade. No logging workspace, managed HSM, premium vault or Marketplace product is needed.

Use vault-scoped Azure RBAC. The authenticated operator needs secret-set permission, and the same intended human owner needs secret-read permission. If the operator and owner are the same principal, a vault-scoped **Key Vault Secrets Officer** assignment can perform the one-time write/read/disable lifecycle; do not grant it subscription-wide. Management-plane Owner alone does not automatically grant secret-data access under Key Vault RBAC. Allow propagation before treating a denial as a failed vault.

Store the bootstrap-only file without printing the returned secret object:

```bash
az keyvault secret set \
  --vault-name VAULT_NAME \
  --name voqro-owner-bootstrap \
  --file /private/path/owner-bootstrap.txt \
  --encoding utf-8 \
  --only-show-errors --output none
```

Give the user the ordinary Azure portal **vault resource link**, which contains no secret:

```text
https://portal.azure.com/#resource/subscriptions/SUBSCRIPTION_ID/resourceGroups/RESOURCE_GROUP/providers/Microsoft.KeyVault/vaults/VAULT_NAME/overview
```

In the portal, the owner opens **Objects → Secrets → voqro-owner-bootstrap → current version → Show Secret Value**. They then open `https://voqro.vercel.app/setup`, paste the secret into the bootstrap field, enter their configured email and choose their own password. The secret and password must stay in those trusted forms, not in chat. No authorization callback code is collected by the assistant.

The setup URL may differ if the approved frontend origin changes. It must be the actual HTTPS deployment, and the cookie/session check must pass through the same public origin.

## 4. Retire one-time setup

After the backend confirms bootstrap is consumed and the owner can sign in:

- Disable the Key Vault secret (`az keyvault secret set-attributes --vault-name VAULT_NAME --name voqro-owner-bootstrap --enabled false --output none`). Do not display its value to verify this.
- Remove the bootstrap secret from the persistent application environment through an explicitly reviewed root-only file update. Keep the bootstrap-complete database marker; do not delete it. Restart only after confirming the container startup check supports completed bootstrap without the initial secret.
- Remove the completed Managed Run Command resource and the temporary private local body/bootstrap files after verifying successful provisioning. Preserve the installed root-only environment and database. Do not erase unknown files or existing backups.
- Retain or remove the bootstrap vault and its vault-scoped permissions according to the user's intended recovery policy; no automatic deletion of unrelated resources.

There is no emailed password reset provider in this initial setup. Future password recovery must use a separately implemented, verified recovery path. Do not replace that with reusable shared owner credentials.
